01
What is an API?

A controlled way for one software system to request data or action from another system.

SCRIPT: “API means Application Programming Interface. Ayaw kahadlok sa term. Think of it as a waiter in a restaurant. You do not enter the kitchen and cook. You give a request through the waiter, the kitchen processes it, and the waiter brings back the result. The API is the waiter, the system is the kitchen, and the response is your order.”
Analogy

API as a restaurant waiter

  • Client: the customer making a request
  • API: the waiter receiving and translating it
  • Server: the kitchen doing the work
  • Response: the meal or message returned
  • Rules: the menu, ordering format, and permissions

Bisaya shortcut: “Ang API mao ang messenger nga naay rules. Dili siya free-for-all access.”

SCRIPT: “The restaurant analogy helps us understand control. The waiter does not allow you to enter the kitchen and touch anything. The menu limits what you can request. The kitchen returns a response. In an API, the documentation is like the menu, authentication is like checking the customer, and authorization is like checking whether you are allowed to order a particular item.”
API Vocabulary

Five words you must know

Endpoint

A specific address where a service can be requested, such as “get customer” or “create invoice.”

Request

The message sent by the client, including method, parameters, credentials, and data.

Response

The result returned by the server, including data or an error message.

Authentication

Proving who or what is making the request.

Authorization

Checking what the authenticated requester is allowed to do.

Rate limit

A rule that controls how many requests can be made in a time window.

SCRIPT: “Authentication and authorization are different. Authentication asks, ‘Kinsa ka?’ Authorization asks, ‘Unsa imong pwede buhaton?’ A user can be authenticated but still not authorized to delete transactions. That distinction matters in accounting controls.”
Methods

Common API actions

MethodPlain meaningAccounting example
GETRetrieve informationGet unpaid invoices
POSTCreate a new record or actionCreate an invoice
PUT/PATCHUpdate an existing recordChange invoice status
DELETERemove a record, where allowedDelete a draft, not a posted entry

Control principle: The more destructive the action, the stronger the authorization and audit evidence should be.

SCRIPT: “These methods describe intent. GET reads. POST creates. PUT or PATCH updates. DELETE removes, although many financial systems avoid hard deletion once a transaction is posted. If an API can delete financial data, access must be tightly restricted and logged.”

Integration patterns

Different business problems require different ways of connecting systems.

SCRIPT: “Integration is not one thing. We choose a pattern based on speed, volume, complexity, cost, and risk. Four patterns are especially useful for AIS analysis.”
Pattern 1

Point-to-point integration

System A connects directly to System B. Simple at first, but difficult to manage as connections multiply.

POS
→
Accounting

Use when: one stable connection is needed and the scope is small. Risk: many direct connections create a fragile web.

SCRIPT: “Point-to-point is like a direct road between two towns. Fast and simple. But if every town builds a road to every other town, the map becomes expensive and confusing. That is the same problem when a business connects every application directly to every other application.”

Pattern 3

Event-driven integration

One system publishes an event, and subscribed systems react automatically.

EventSubscriberAction
Invoice approvedLedgerCreate payable entry
Payment receivedCustomer portalUpdate account status
Stock below thresholdPurchasingCreate reorder alert
Employee paidGeneral ledgerPost payroll summary
SCRIPT: “Event-driven integration is like a notification. Something happens, and interested systems react. The benefit is speed and decoupling. The risk is that events can be duplicated, delayed, or missed, so we need unique IDs, retry logic, and monitoring.”
Pattern 4

Batch integration

Data is collected and transferred on a schedule, such as hourly, nightly, or monthly.

Good for

Large volumes, stable schedules, legacy systems, and processes that do not require instant updates.

Example

Upload daily POS totals to the accounting system at 11:00 PM.

Risk

Errors may remain hidden until the next batch and reports may lag behind reality.

SCRIPT: “Batch is not outdated. It can be cost-effective and reliable when the business does not need real-time data. A nightly sales summary may be enough for a small business. The important question is whether the delay creates business or control risk.”
Real-time vs Batch

Choose speed based on the decision

NeedBetter fitReason
Fraud alert during paymentReal-timeAction must happen immediately
Daily branch sales reportBatchHourly data may not change the decision
Available cash balanceNear real-timeManagers need current information
Monthly payroll postingBatchScheduled and controlled processing
SCRIPT: “Do not demand real-time just because it sounds modern. Ask what decision depends on the data. If an immediate action is required, real-time is justified. If not, a controlled batch may be cheaper and simpler.”
Accounting Data Flow

From sale to financial report

  1. Customer buys through POS or e-commerce
  2. Sales event is recorded
  3. Payment provider confirms settlement
  4. Inventory and tax values are updated
  5. Ledger receives a mapped entry
  6. Reconciliation confirms totals
  7. Report presents the result to management
SCRIPT: “This is the chain an accountant should trace. Do not jump directly to the report and assume it is correct. Follow the source transaction, settlement, inventory, tax, mapping, reconciliation, and report. Each step can introduce error.”
Data Mapping

Integration fails when meanings do not match

Source fieldTarget fieldMapping question
POS item categoryLedger revenue accountWhich account receives the sale?
Payment typeCash/bank clearing accountWhere is settlement recorded?
VAT flagTax codeDoes the tax treatment match?
Branch codeDepartment dimensionCan management report by branch?

“Same word” does not guarantee same meaning. Mapping must be documented and tested.

SCRIPT: “A system can transfer data successfully and still produce wrong accounting if the meanings do not match. Data mapping is where business knowledge matters. You need to understand the source field, the target field, and the accounting rule behind it.”
Integration Controls

Six controls for trustworthy data exchange

Authentication

Use secure keys, tokens, or certificates.

Authorization

Limit actions and data scope.

Validation

Reject incomplete or invalid records.

Idempotency

Prevent duplicate processing when a request is retried.

Monitoring

Track successes, failures, latency, and unusual volume.

Reconciliation

Compare source totals with target totals.

SCRIPT: “These controls should appear in every integration conversation. Authentication and authorization protect access. Validation protects data quality. Idempotency prevents duplicate invoices or payments. Monitoring tells us when something fails. Reconciliation proves that the flow is complete and accurate.”
Failure Handling

What happens when an API call fails?

  • Capture a clear error message and transaction ID
  • Retry only when the failure is temporary and safe to retry
  • Use duplicate protection before reprocessing
  • Send failed records to an exception queue
  • Notify the responsible team with enough context
  • Document resolution and update the control log
SCRIPT: “A failed API call is not just an IT issue. If the invoice did not reach the ledger, financial reports may be incomplete. Good systems do not hide failures. They preserve the record, explain the error, and give people a controlled way to resolve it.”
Mini Case

Case: café POS to accounting integration

A three-branch café wants hourly sales reporting. The POS sends sales, refunds, discounts, payment type, branch, and tax data to the cloud ledger. Management complains that daily totals sometimes differ.

Likely causes

Duplicate retries, missing refunds, wrong branch mapping, delayed settlement, or tax-code mismatch.

Evidence to request

Source totals, integration logs, failed records, mapping table, and reconciliation report.

First control

Daily control-total reconciliation by branch, payment type, and tax category.

SCRIPT: “Do not guess. Start with evidence. Compare source POS totals to ledger totals by branch, payment type, and tax. Then inspect failures and mapping. This is how an accountant turns a vague complaint into a structured investigation.”

Integration walkthrough

A control-minded navigation pattern for reviewing a data connection

SCRIPT: “Let us walk through an integration review. We will use a generic SaaS layout so the method transfers across products.”
Walkthrough Step 1

Confirm connection identity

  1. Open Settings → Integrations or Connected Apps
  2. Confirm the correct organization and environment
  3. Check connected account or service principal
  4. Review permissions or scopes
  5. Confirm last successful sync time
SCRIPT: “Start by confirming you are looking at the correct organization. Then check who or what is connected, what permissions exist, and when the last successful sync happened. Never troubleshoot blindly.”
Walkthrough Step 2

Inspect the data path

  1. Open field mapping or integration configuration
  2. Trace source fields to target fields
  3. Check tax, account, branch, and currency rules
  4. Review filters and excluded records
  5. Confirm the schedule or event trigger
SCRIPT: “Next, inspect the data path. Which source fields map to which target fields? Are refunds included? Are foreign currencies converted? Are some records excluded? A hidden filter can explain a missing transaction.”
Walkthrough Step 3

Review logs and reconcile

  1. Open activity, sync, or audit logs
  2. Filter failed and retried records
  3. Export a sample of transaction IDs
  4. Compare source and target control totals
  5. Document exceptions and owner

Deliverable: a one-page integration review note with status, evidence, exceptions, and next action.

SCRIPT: “End with evidence. Logs tell us what the integration says it did. Reconciliation tells us whether the business result agrees. Document exceptions and assign an owner. That turns a technical review into an auditable workpaper.”

Professional Judgment

Integration is business design

  • Start with the process and decision, not the API feature
  • Define ownership for every data element
  • Document mapping and exception handling
  • Reconcile before trusting reports
  • Protect credentials and minimize permissions
  • Design for change, failure, and exit
SCRIPT: “The biggest takeaway: integration is not only technical. It is business process design. If ownership, mapping, exceptions, and reconciliation are unclear, the integration will create automated confusion.”
Wrap-up

Six ideas to remember

  • API = controlled request and response between systems.
  • Authentication proves identity; authorization limits action.
  • Integration patterns include point-to-point, hub, event-driven, and batch.
  • Data mapping translates business meaning across systems.
  • Validation, idempotency, monitoring, and reconciliation are essential controls.
  • Trace transactions from source to report before trusting the output.
SCRIPT: “That is our lesson. In your future work, you may not write the integration code, but you will define the accounting requirements, review the controls, investigate exceptions, and decide whether the reports are trustworthy. That is a very valuable role.”
